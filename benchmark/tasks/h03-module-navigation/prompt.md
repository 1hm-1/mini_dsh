# Route resolution in the request entry point

`dispatch(path)` from `entry.mjs` is the application entry point. It receives an absolute URL pathname string (no query string) and returns `{ route, params }`. Invalid paths (not a string, empty, or not beginning with `/`) throw `TypeError`. Do not change the pathname text: matching is case sensitive, and a trailing slash is distinct from the route without it. The route ID is a string; `params` is a new plain object. The default routes in `fixtures/routes.mjs` are the production route table used by `dispatch`. `resolveFromRegistry(path, records)` is the lower-level exported resolver and uses the same matching policy for supplied records.

Supplied `records` are guaranteed to be an array of valid records; invalid record shapes are outside this task. Route IDs and static paths are strings. Dynamic parameter names are unique within each pattern, nonempty, and match `[A-Za-z][A-Za-z0-9]*`; matching paths remain plain pathname strings. Records have one of three shapes: `{ kind: 'static', path, route }`, `{ kind: 'dynamic', pattern, route }`, or `{ kind: 'fallback', route }`. Static paths are exact. A dynamic pattern starts with `/` and uses `:name` for a whole, nonempty path segment; it may contain literal segments. On a match, return parameters with the original segment values. Among matching records, any static route wins over any dynamic route regardless of declaration order; otherwise the first matching dynamic route wins; fallback is considered only if neither matched. Within static matches, use the first declared static record; if multiple fallbacks exist, use the first declared fallback. With no match and no fallback, return `null`. All records and returned values must be left independent of later calls; do not mutate records. The fixture deliberately lists a dynamic `/users/:id` before the static `/users/new` and includes a fallback to expose ordering.

Keep `legacyResolve(path)` in `legacy.mjs` and its old `/old/help` behavior unchanged. It is a separate compatibility API, not the production entry point. The HTTP/CLI adapters and path/query/header utilities have separate responsibilities and must continue to behave as their exported APIs specify; they are included because they are real users or support modules, not as instructions to edit them. Edit only the writable files.
