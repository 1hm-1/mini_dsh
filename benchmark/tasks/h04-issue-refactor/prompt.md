# Issue: make all issue views use the same normalization

The issue board has several small consumers that grew separately. A list page, search results, an activity export, and the JSON export now disagree on order and on how they display tags and assignees. Please repair the shared transformation and the affected consumers without changing the public entry names. The workspace includes example records, a legacy title helper, and date/page/console helpers used by neighboring board features. Their behavior is part of the compatibility surface; this work is confined to the five writable source files.

## Record contract and shared transformation

A raw issue is a non-array object with own fields `id`, `title`, `tags`, and `assignee`. `id` must be a string whose trimmed value is nonempty; `title` must be a string (it may trim to empty); `tags` must be an array of strings; `assignee` must be a string or `null`. Additional fields may exist but are not copied to normalized output. A malformed issue must throw `TypeError` with message `invalid issue`. `normalizeIssue(issue)` returns a fresh object whose property order is `id`, `title`, `tags`, `assignee`. Trim the ID and title but preserve their case. For tags, trim each label, lowercase it with JavaScript `toLowerCase()`, omit empty labels, then keep only the first occurrence of each normalized label in its original order. The resulting tags array must be new. For a string assignee, trim and lowercase it; empty or whitespace-only becomes `null`. An input `null` assignee remains `null`. Never mutate the record or nested tags array; frozen inputs must work.

For example, `{ id: ' B-2 ', title: '  Fix API  ', tags: [' UI ', 'ui', '', 'BackEnd'], assignee: ' Ada ' }` normalizes to `{ id: 'B-2', title: 'Fix API', tags: ['ui', 'backend'], assignee: 'ada' }`. A raw issue with `assignee: null` stays unassigned. The display title stays `Fix API`, not `fix api`. This intentionally differs from tag and assignee casing.

## Consumers and stable order

`listIssues(issues)` accepts only an array (`TypeError('issues must be an array')` otherwise), returns a fresh array of normalized issues, and preserves input order exactly. Duplicate IDs are allowed and remain separate entries. `searchIssues(issues, query)` uses that same normalized list; query must be a string (`TypeError('query must be a string')` otherwise). Trim and lowercase the query, then return matching issues in original order when the query is a substring of the normalized title (case insensitive) or of any normalized tag. Empty/whitespace query returns the whole normalized list. Search does not match IDs or assignees. Search must not mutate records or reuse an output array across calls.

`activityLines(issues)` also uses the normalized list in input order. Each line is `id|assignee|tags`, where a null assignee is rendered as `-` and tags are joined by commas without spaces. Empty tags produce an empty final field, for example `B-2|-|`. It returns a fresh array of strings. `serializeIssues(issues)` returns JSON text of the same normalized array as `listIssues`, preserving that array order and the normalized object's property order. Do not serialize raw objects or extra fields. All four consumers must propagate list/record validation errors as stated above.

## Compatibility and examples

Keep `legacyTitle(issue)` exported from `legacy.mjs`: it returns `String(issue.title).trim()` and is intentionally a separate older API, including its behavior on values other than strings. Keep `boardSnapshot(issues)` from `api.mjs` returning `{ issues: listIssues(issues), activity: activityLines(issues) }` with those keys in that order. The example fixture is illustrative, not a hidden source of defaults. Date formatting, paging, and console display are unrelated exports and should keep their existing behavior. The old `legacyTitle` helper must not be replaced by `normalizeIssue`; a caller may still pass `{ title: 3 }` to that old helper.
